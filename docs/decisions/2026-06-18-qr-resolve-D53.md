## THE DECISION

**Three jobs a URL plays. Conflating them was the original bug.**

### 1. The QR points at TRACE, never at the tenant's own site

A QR code whose scan target is the tenant's own website (`lawnstrees.com/...`) is a **MISMATCH TO
FIX**, not a configuration to support. The tenant's site is a **dead end** for this flow:

- no cart
- no customer capture
- no session

Whatever the tag physically says, the *destination* is TRACE.

### 2. The tenant's URL is BRANDING on the page TRACE serves

The tenant's domain, name, and identity appear **on the page TRACE renders**. One app, skinned per
tenant. The tenant's URL is a presentation fact, never a routing fact. (This is AC-4 — structure is
shared, only tokens and vocabulary vary per vertical/tenant.)

### 3. An existing tag pointing at their site is handled by STRIP-AND-RESOLVE

We do not require a tenant to re-print tags they already own. The rule:

> **Strip the URL. Keep the identifying part. Resolve it against tenant-scoped inventory.**

And its corollary, which is the part that keeps the model clean:

> **Capture and count are URL-AGNOSTIC.** They are operator-facing and tenant-scoped, and the
> customer-facing URL never enters that path.

## STATUS OF THE BUILD — the design and the code AGREE

What was settled on 2026-06-18 was the **method**. What was genuinely unknown until 2026-08-01 was
whether it had been **built**. It has. Recorded here so nobody re-opens it a seventh time:

**The strip** — [`packages/cultivar-os/src/lib/scanTag.ts`](../../packages/cultivar-os/src/lib/scanTag.ts)
`extractTag(raw)`: matches `/plant/<tag>` and returns the tag; failing that, takes the last path
segment of any other URL; failing that, uses the raw string as-is. Its own header states the rule:
*"a scanned QR holds a URL like `https://…/plant/SCV-0031`; strip the URL, keep the tag."* It is
ONE definition shared by the walk-and-count loop and the multi-item scan-order loop (§6 r8).

**The resolve** — a ladder over a bare string, **column-agnostic by design**:

| Lane | Target | Home |
|---|---|---|
| **L1** | `cultivar_plants.tag_id` (exact, `ilike`) — the most-specific VERTICAL lane | caller: [`usePlant.ts:101-107`](../../packages/cultivar-os/src/hooks/usePlant.ts#L101-L107), [`InventoryCount.tsx:260-263`](../../packages/cultivar-os/src/pages/InventoryCount.tsx#L260) |
| **L2** | `business_inventory.sku` (exact, `ilike`) | [`stockLineResolver.ts`](../../packages/shared/src/inventory/stockLineResolver.ts) |
| **L4** | NAME token-set EQUALITY (order-insensitive) | `stockLineResolver.ts` + `utils/canonicalName` |
| **L5** | SIZE-picker on a same-variety multi-size collision; genuinely ambiguous → miss | `stockLineResolver.ts` `detectSizeCollision` |

The shared resolver is deliberately **AC-1 clean** — it names no vertical table. Its header:
*"The most-specific vertical lane (a `cultivar_plants` tag_id) stays in each caller — this module is
AGNOSTIC."* The vertical lane lives in the caller; the generic lanes live in shared code.

**Therefore: the resolver is not "pointed at the wrong table." It is pointed at BOTH, in priority
order, which is exactly what strip-and-resolve specifies.** A tag that is a specimen id resolves at
L1; a tag that is a lot SKU resolves at L2; a tag that is a variety name resolves at L4. This is the
decision, built.

**Capture and count are URL-agnostic, as ruled** — `InventoryCount` runs the same ladder against a
`business_id`-scoped read and never touches the customer-facing URL.

## WHAT THIS DECISION DOES *NOT* COVER

Recorded so the boundary is explicit and the next reader does not mistake a different gap for this
one:

1. **Nothing in the platform PRINTS a tag.** `generatePlantQR` and `printQRLabel`
   ([`shared/src/qr/generate.ts`](../../packages/shared/src/qr/generate.ts),
   [`shared/src/qr/print.ts`](../../packages/shared/src/qr/print.ts)) have **zero callers**. The only
   live QR consumers are team-invite and profile links via the generic `generateQR`. This is a real
   gap in the operator story (see `user_stories.md` → *Operator scan*), **not** a defect in resolve.
   Note also: `generatePlantQR(plantId)` builds its URL from an **id**, while the route and every
   resolver lane key on a **tag/sku** — a latent mismatch if it is ever wired.
2. **The ANON entry point.** [`usePlant.ts:137`](../../packages/cultivar-os/src/hooks/usePlant.ts#L137)
   gates the L2→L5 lanes on `if (businessId)`, so a guest with no session runs L1 only. That is a
   **separate, deliberate, documented** limitation belonging to the guest-scan story — see
   [D-54](2026-06-03-gated-price-key-D54.md) and `user_stories.md` → *On-lot guest scan*. It is not
   a resolve-model question.
3. **Which table is the anchor.** That is **[D-34]** ("the lot is the SKU"), already decided.
   D-53 governs how a scanned STRING becomes a row; D-34 governs which row a SALE anchors on.

## RELATION TO OTHER DECISIONS

- **Implements the scan half of [D-34]** (the lot is the SKU). D-34 says the lot is the anchor;
  D-53 says how any tag — specimen, SKU, or name — reaches it.
- **AC-1:** the shared resolver names no vertical table; the vertical lane stays in the vertical's
  own caller.
- **AC-3:** every generic lane is `business_id`-scoped. Tenant-scoped resolution is part of the rule
  as stated ("resolve it against **tenant-scoped** inventory"), not an implementation detail.
- **AC-4:** job 2 (the tenant URL is branding) is AC-4 applied to identity.

## GUARD

**None.** There is no mechanical check that a QR target points at TRACE rather than a tenant domain,
and none that the resolver ladder keeps its lane order. Recorded as `—` per the RULINGS.md
convention: *a ruling with no guard is a ruling waiting to be broken by someone who knows it.*

Worth noting the guard that would have helped most was not a lint — it was **this file existing**.
